# Deploy do Fadex Helpdesk

Escrito em 15/08/2026, com `dev` em `f66b43e`.

Este documento prepara o deploy; ele **não foi executado**. Não há conta provisionada em nenhuma
plataforma, nenhum domínio e nenhum certificado. Tudo o que aparece aqui como "verificado" foi
verificado localmente, com Docker; o que não foi está listado no final, em
[O que não foi validado](#o-que-nao-foi-validado).

---

## 1. Antes de qualquer coisa: dois bloqueadores no código

São mudanças de **código**, fora do alcance desta frente (`backend/src/**` e `frontend/src/**`
pertencem a outras frentes). Sem a primeira, o sistema **não funciona** em produção.

### 1.1 O frontend ignora `NEXT_PUBLIC_API_BASE_URL` — bloqueador absoluto

`frontend/src/config/public-env.ts` lê o ambiente assim:

```ts
export function getPublicEnv(
  env: Record<string, string | undefined> = process.env
): PublicEnv {
```

O Next.js só substitui **acessos literais** do tipo `process.env.NEXT_PUBLIC_X` no bundle do
navegador. Uma referência ao objeto `process.env` inteiro não sobrevive ao build: o webpack a
remove, o `safeParse` do zod não encontra a chave e o `.default("http://localhost:8080/api/v1")`
assume.

Verificado, e não deduzido:

```
docker build --build-arg NEXT_PUBLIC_API_BASE_URL=https://exemplo.invalid/api/v1 -t teste ./frontend
docker run --rm --entrypoint sh teste -c "grep -ro 'exemplo.invalid' .next/static | wc -l"
# 0
docker run --rm --entrypoint sh teste -c "grep -ro 'localhost:8080'   .next/static | wc -l"
# 62 — o default do código, dentro dos chunks do navegador
```

Consequência: publicado em `https://helpdesk.exemplo.com.br`, o navegador do usuário chamaria
`http://localhost:8080/api/v1`. Falha 100% das requisições. **Passa despercebido em
desenvolvimento**, porque nessa máquina o backend realmente está em `localhost:8080` — é o único
ambiente em que o bug é invisível.

Correção sugerida à frente de frontend (mantém o parâmetro injetável, que os testes usam):

```ts
const inlinedPublicEnv: Record<string, string | undefined> = {
  NEXT_PUBLIC_APP_NAME: process.env.NEXT_PUBLIC_APP_NAME,
  NEXT_PUBLIC_API_BASE_URL: process.env.NEXT_PUBLIC_API_BASE_URL
};

export function getPublicEnv(
  env: Record<string, string | undefined> = inlinedPublicEnv
): PublicEnv {
```

Verificado com uma cópia do frontend fora da árvore de trabalho (nenhum arquivo de outra frente foi
tocado): com esse ajuste, `exemplo.invalid` passa a aparecer **6 vezes** em `.next/static`.

### 1.2 `JWT_SECRET` tem default público no código

`backend/src/main/resources/application.properties`:

```
security.jwt.secret=${JWT_SECRET:trocar-por-valor-local-com-pelo-menos-32-caracteres}
```

O default é um texto versionado em repositório. Quem o conhece assina um JWT válido e se apresenta
como ADMIN. **Em produção o correto é não subir** sem a variável.

O `docker-compose.prod.yml` já resolve isso pelo caminho de configuração: `${JWT_SECRET:?...}` faz
o `docker compose` abortar antes de criar qualquer container. Mas a guarda vive na **interpolação
do Compose** — um deploy que injete variáveis direto na imagem (PaaS, Kubernetes, `docker run`)
passa por fora dela e volta a usar o default.

Correção definitiva, uma linha, para a frente de backend: trocar por `${JWT_SECRET}` sem default.
O Spring falha no boot com `Could not resolve placeholder`, que é exatamente o comportamento
desejado.

### 1.3 Achados menores, para registro

- **`classificationOrigin` diz `IA` mesmo quando quem classificou foi a heurística.** Medido: com
  `AI_TRIAGE_ENABLED=false`, um chamado criado voltou com `classificationOrigin: "IA"`,
  `confidence: 0.6` e `classificationJustification: "Classificacao por fallback deterministico
  baseado em palavras-chave."`. Só a justificativa conta a verdade. Numa instância pública sem IA,
  a tela afirma "IA" para tudo. Sugestão: um valor `HEURISTICA` em `ClassificationOrigin`.
- **Com a IA desligada, cada chamado deixa um job de `EMBEDDING` em `FAILED`** com a mensagem
  "Triagem IA desabilitada para embeddings." (`AiJobWorker.process`). Medido: `attempts` para em 1,
  então **não há laço de retentativa** — é cosmético, mas polui `GET /api/v1/ai/jobs`. Sugestão:
  não enfileirar o job de embedding quando a triagem está desligada.
- **O frontend não usa `output: "standalone"`.** A imagem carrega `node_modules` inteiro e pesa
  **1 GB**; com `standalone` cairia para a casa de 200 MB. Não alterei `next.config.ts` para não
  mudar a saída de build debaixo de outra frente.

## 2. A decisão sobre a IA em produção

### 2.1 Os números

Tamanho das imagens, `docker images` nesta máquina:

| Imagem | Tamanho |
| --- | --- |
| `ollama/ollama:latest` | **8,35 GB** |
| `fadex-helpdesk-frontend` | 1,00 GB |
| `pgvector/pgvector:pg17` | 627 MB |
| `fadex-helpdesk-backend` | 414 MB |
| `llama3.2:3b` (modelo) | 2,0 GB |
| `all-minilm` (modelo) | 45 MB |

- **Sem IA**: 627 MB + 414 MB + 1,00 GB ≈ **2,0 GB** de disco antes do primeiro registro.
- **Com IA**: some 8,35 GB da imagem do Ollama e 2,05 GB de modelos ≈ **12,4 GB**.

Memória, medida com `docker stats --no-stream`:

| Serviço | RSS medido |
| --- | --- |
| backend (JVM, ocioso após seed) | **423 MiB** |
| frontend (Next.js em produção) | 80 MiB |
| postgres | 51 MiB |
| ollama ocioso, modelos descarregados | 20 MiB |
| ollama com `llama3.2:3b` + `all-minilm` carregados | **~2,7 GB** |

O último número vem de `ollama ps`: 2,6 GB para o `llama3.2:3b` e 48 MB para o `all-minilm`. Com
três modelos residentes o container marcou 3,96 GiB.

Latência, com 12 vCPU e sem GPU:

| Chamada | Tempo |
| --- | --- |
| primeira classificação (inclui carregar o modelo) | 29,4 s |
| classificação com modelo quente, `llama3.2:3b` | **12,4 s** |
| classificação com modelo quente, `llama3.2:1b` | 12,8 s |
| embedding, `all-minilm` | **0,03 s** |

Esse é o número mais desconfortável. `AI_REQUEST_TIMEOUT_SECONDS` é **20 s**. Numa máquina de 2
vCPU — o tamanho que a IA já obriga a pagar — 12 s viram bem mais que 20, e o efeito é queda
silenciosa para a heurística, registrada apenas como `WARN` no log. Ou seja: **pagar por um VPS
grande o bastante para carregar o modelo ainda não garante que ele responda a tempo.** Só CPU
rápida ou GPU resolvem, e GPU muda a ordem de grandeza do preço.

### 2.2 Os três cenários

**Cenário A — sem Ollama, `AI_TRIAGE_ENABLED=false`. É a recomendação.**

Custo zero de infraestrutura de IA. Cabe em qualquer VPS de 2 GB. O que se ganha e o que se perde:

- A classificação **continua acontecendo**, pelo `FallbackTicketClassifier` (palavras-chave).
  Verificado nesta configuração: um chamado "Impressora do financeiro parada" foi classificado como
  `EQUIPAMENTOS`, com `MEDIA` de prioridade e `confidence` 0,6.
- A qualidade é a medida em `docs/projeto/2026-08-15-proximos-passos.md`: **5/10 em categoria**. Os
  6/10 de prioridade são viés de classe majoritária — a heurística responde `MEDIA` em 9 dos 10
  casos. O exemplo acima ilustra a fragilidade: a palavra-chave cadastrada é `parado`, o chamado diz
  `parada`, e a prioridade não sobe.
- **A detecção de duplicados desaparece por completo.** Não degrada: some. Ela depende dos
  embeddings, os embeddings dependem do Ollama, e o `AiJobWorker` marca todo job de `EMBEDDING` como
  falho quando `AI_TRIAGE_ENABLED=false`. Sem embedding gravado, `DuplicateDetectionService` não
  tem o que comparar e nenhum `ticket_link` é criado.
- É preciso **dizer isso na tela ou no README**, não só aqui. Ver o achado 1.3 sobre o
  `classificationOrigin` mentindo `IA`.

**Cenário B — com Ollama.** Exige, medido: **~2,7 GB** só para os modelos residentes, mais ~550 MB
do resto da stack, mais folga para o pico de contexto e para o sistema operacional.

- **RAM mínima realista: 6 GB. Recomendado: 8 GB.** Com 4 GB o Ollama e a JVM disputam memória e o
  OOM killer decide quem morre.
- **Disco: 20 GB**, pelos 12,4 GB de imagens mais volumes e camadas intermediárias de build.
- Isso é a faixa de VPS de 8 GB, que hoje custa na ordem de 15 a 30 EUR/mês. Nenhum tier gratuito
  chega perto — os gratuitos entregam 256 MB a 1 GB de RAM e nem a imagem de 8,35 GB cabe no disco.
- E, ainda assim, o item da latência acima continua de pé: 2 vCPU não classificam dentro dos 20 s.

**Cenário C — provedor de LLM por API.** Não implementado, e o caminho já existe: a interface
`AiTriageClient` tem uma única implementação (`LocalAiTriageClient`). Uma segunda implementação,
escolhida por propriedade, roda em torno de uma hora e elimina os 8,35 GB, os 2,7 GB de RAM e os
12 s de latência de uma vez — o cenário A com qualidade melhor que a do Ollama local.

Dois cuidados registrados em `docs/projeto/2026-08-15-proximos-passos.md`, que valem repetir: a
chave **nunca** com prefixo `NEXT_PUBLIC_` (isso a publica no navegador), e uma instância pública
com as credenciais de seed no README significa que qualquer pessoa consome a chave criando
chamados — logo, limite de gasto configurado no provedor.

Os embeddings também teriam de migrar junto, e aí há custo de banco: a coluna é `vector(384)`, e
um provedor com outra dimensão exige migration nova.

### 2.3 Recomendação

**Subir no cenário A**, com `AI_TRIAGE_ENABLED=false`, e deixar o cenário B a um comando de
distância (`--profile ia`) para quem tiver a máquina. É o que o `docker-compose.prod.yml` faz: um
arquivo só, os dois cenários.

O argumento não é preço, é honestidade. Com `llama3.2:1b` — o modelo que caberia num VPS pequeno —
a medição registrada é **3/10 em categoria e 1/10 em prioridade**, pior que a heurística de
palavras-chave em ambos. Pagar 20 EUR/mês e esperar 12 s por uma classificação **pior** que a
gratuita e instantânea não se sustenta. O que a IA local entrega de fato, e bem, é a **detecção de
duplicados** (cosseno 0,857 para duplicata parafraseada contra 0,43 de ruído) — essa sim é a perda
real do cenário A, e é ela que deve ser citada quando alguém perguntar o que falta na instância
publicada.

## 3. Banco: pgvector

A migration `V3` cria a extensão, a coluna `vector(384)` e um índice HNSW. Os três pontos estão
externalizados como placeholders do Flyway em `application.properties` — uma costura deliberada, já
usada pelo perfil de teste para rodar em H2.

Detalhe que muda a conversa: **a similaridade não é calculada pelo pgvector**.
`DuplicateDetectionService` lê os embeddings como texto (`select cast(embedding as varchar) ...`) e
calcula o cosseno em Java (`EmbeddingSimilarity.cosine`). O pgvector é usado apenas como tipo de
coluna, índice e no `cast(:embedding as vector)` da gravação — caminho que só executa quando a IA
está ligada.

Consequência prática: **no cenário A a aplicação roda em Postgres comum, sem extensão nenhuma.**

Verificado subindo a stack contra `postgres:17-alpine` com os placeholders sobrescritos:

```
SPRING_APPLICATION_JSON={"spring.flyway.placeholders.pgvector-extension":"select 1",
                         "spring.flyway.placeholders.ticket-embedding-column-type":"text",
                         "spring.flyway.placeholders.ticket-embedding-index":"select 1"}
```

Resultado: `Successfully applied 7 migrations`, `Started HelpdeskApplication`, login com as
credenciais do seed devolvendo 200, criação de chamado devolvendo 201, `GET /indicators` devolvendo
200 e a classificação por heurística concluída pelo worker. O valor pronto está comentado em
`.env.producao.example`.

**Isso só vale com `AI_TRIAGE_ENABLED=false.** Com a IA ligada, a gravação do embedding faz
`cast(? as vector)` e falha numa coluna `text`.

### Provedores

A regra segura é a que não depende de fornecedor: **rodar `pgvector/pgvector:pg17` no próprio
compose**, como o `docker-compose.prod.yml` faz. Sem depender de catálogo de extensão de ninguém.

Se for usar Postgres gerenciado, pgvector é hoje comum entre os provedores voltados a aplicação —
[Neon](https://neon.com/docs/extensions/pgvector) documenta o suporte em todos os planos,
[Railway](https://railway.com/deploy/postgres-with-pgvector-engine) publica um template com a
extensão, e Supabase e AWS RDS aparecem na mesma lista em
[levantamentos recentes](https://www.bytebase.com/blog/pgvector/). **Confirme no painel do provedor
escolhido antes de contratar** — catálogo de extensão muda, e este documento não foi testado contra
nenhum deles.

Duas armadilhas mesmo onde há suporte:

1. `CREATE EXTENSION IF NOT EXISTS vector` é executado **pelo Flyway, com o usuário da aplicação**.
   Alguns provedores exigem superusuário ou habilitação prévia pelo painel. Se for o caso, habilite
   a extensão antes do primeiro deploy — a partir daí o `IF NOT EXISTS` torna a migration inócua.
2. Quase todos exigem TLS: acrescente `?sslmode=require` ao `DB_URL`.

Se o provedor **não** tiver pgvector: use o `SPRING_APPLICATION_JSON` acima e aceite o cenário A.
Não há terceira saída — sem a extensão não há como gravar a coluna vetorial.

## 4. Artefatos desta frente

| Arquivo | Para quê |
| --- | --- |
| `docker-compose.prod.yml` | Stack de produção. Não substitui o compose de desenvolvimento. |
| `.env.producao.example` | Modelo de ambiente, com as cinco variáveis obrigatórias em branco. |
| `.gitignore` | Exceção para versionar o `.example` (`.env.*` era ignorado por inteiro). |
| `.env.example` | Correção de um comentário desatualizado sobre repasse de variáveis. |

Diferenças deliberadas em relação ao compose de desenvolvimento:

- Variáveis críticas com `${VAR:?mensagem}`: **o Compose aborta** sem elas.
- Sem Mailpit. Produção exige SMTP real.
- Postgres **sem porta publicada** — só a rede interna alcança o banco.
- Ollama e o baixador de modelos no profile `ia`, ausentes por padrão.
- `restart: always` no lugar de `unless-stopped`.
- `SPRING_DATASOURCE_*` no lugar de `DB_*` (ver a seção 5.3 — é obrigatório).
- `healthcheck` no backend contra `/api/v1/choices`, que é público e toca o contexto inteiro do
  Spring. O projeto não tem Actuator, logo não existe `/actuator/health`. Verificado: a imagem do
  backend traz `wget` (`/usr/bin/wget`), o endpoint responde 200 sem token, e o comando exato do
  healthcheck executado dentro do container do backend em execução sai com código 0.
- `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=50`. A JVM dimensiona o heap contra a RAM do **host**,
  porque não há `mem_limit` nos serviços. Numa máquina de 2 GB, 75% dariam um teto de 1,5 GB
  disputando memória com Postgres e Next.js.

## 5. Passo a passo: VPS com Docker

Plataforma concreta e sem letra miúda: uma máquina Linux com Docker. Serve Hetzner, DigitalOcean,
Contabo, Oracle Cloud, uma VM na universidade. Foi para esse formato que a stack foi preparada, e é
o único em que o `docker-compose.prod.yml` funciona como está.

**Tamanho da máquina**, pelos números da seção 2.1: 2 vCPU / 2 GB RAM / 20 GB disco no cenário A.
Cenário B, 8 GB de RAM.

### 5.1 Pré-requisitos

- Acesso SSH com sudo.
- Docker Engine com o plugin Compose (`docker compose version` ≥ v2).
- Um domínio apontando para o IP. Idealmente dois nomes: `helpdesk.seu-dominio` (frontend) e
  `api.helpdesk.seu-dominio` (backend).
- Portas 80 e 443 abertas. **8080 e 3000 não precisam ficar abertas** se houver proxy reverso.

### 5.2 Subir

```bash
git clone <url-do-repositorio> fadex-helpdesk
cd fadex-helpdesk

cp .env.producao.example .env.producao
openssl rand -base64 48        # cole em JWT_SECRET
openssl rand -base64 24        # cole em POSTGRES_PASSWORD
# preencha CORS_ALLOWED_ORIGINS, FRONTEND_BASE_URL e NEXT_PUBLIC_API_BASE_URL com os domínios reais

docker compose -f docker-compose.prod.yml --env-file .env.producao config   # valida
docker compose -f docker-compose.prod.yml --env-file .env.producao up -d --build
docker compose -f docker-compose.prod.yml --env-file .env.producao logs -f backend
```

Um `config` que falha com "required variable X is missing a value" **é a guarda funcionando**, não
um defeito do arquivo.

Para o cenário B, acrescente `--profile ia` em todos os comandos e ponha `AI_TRIAGE_ENABLED=true`
no `.env.producao`. O serviço `ollama-models` baixa os modelos na primeira subida e encerra; a
primeira classificação depois disso é a lenta (29 s medidos), porque carrega o modelo.

### 5.3 Duas coisas que derrubam o deploy e não são óbvias

**`NEXT_PUBLIC_API_BASE_URL` entra na imagem em tempo de build.** Não é variável de runtime. Mudou
a URL da API? A imagem antiga continua apontando para a antiga até que você reconstrua:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.producao up -d --build frontend
```

Reiniciar o container não adianta. Trocar a variável no `.env.producao` e dar `restart` não adianta.
E, enquanto o bloqueador 1.1 não for corrigido, **nem o rebuild adianta** — o valor não chega ao
navegador de jeito nenhum.

**As variáveis `DB_URL`/`DB_USERNAME`/`DB_PASSWORD` não funcionam fora do perfil `dev`.** Elas só
são lidas por `application-dev.properties`, e **não existe `application-prod.properties`** no
projeto. Com `SPRING_PROFILES_ACTIVE=prod` e só as `DB_*`, o backend morre no boot:

```
Failed to instantiate [com.zaxxer.hikari.HikariDataSource]: Failed to determine a suitable driver class
```

Reproduzido e corrigido nesta frente: o `docker-compose.prod.yml` passa `SPRING_DATASOURCE_URL`,
`SPRING_DATASOURCE_USERNAME` e `SPRING_DATASOURCE_PASSWORD`, que o Spring Boot lê sem depender de
perfil. O driver é deduzido da URL. Se a frente de backend criar um `application-prod.properties`,
esta seção pode ser simplificada — mas hoje, sem ela, o deploy não sobe.

### 5.4 TLS e proxy reverso

Publicar 8080 e 3000 direto na internet, em HTTP, funciona para uma demonstração e é ruim para
qualquer outra coisa: o token de login trafega em claro. Com um proxy reverso na frente, mude para
`BACKEND_BIND_ADDRESS=127.0.0.1` e `FRONTEND_BIND_ADDRESS=127.0.0.1` no `.env.producao` e faça o
proxy falar com o loopback.

Um `Caddyfile` mínimo — o Caddy resolve o certificado Let's Encrypt sozinho:

```
helpdesk.seu-dominio {
    reverse_proxy 127.0.0.1:3000
}

api.helpdesk.seu-dominio {
    reverse_proxy 127.0.0.1:8080
}
```

Com HTTPS, `CORS_ALLOWED_ORIGINS`, `FRONTEND_BASE_URL` e `NEXT_PUBLIC_API_BASE_URL` precisam usar
`https://`. Origem em CORS compara esquema: `http://` e `https://` são origens diferentes.

**Atenção ao SSE.** As notificações em tempo real usam uma conexão HTTP longa em
`/notifications/stream`. Proxies com buffering ou timeout curto quebram esse recurso sem erro
visível — a tela apenas para de reagir. Caddy funciona sem ajuste; no Nginx são necessários
`proxy_buffering off` e `proxy_read_timeout` acima de `SSE_TIMEOUT_MS` (30 min por padrão).

### 5.5 Sobre plataformas PaaS

Render, Railway e Fly.io aceitam Dockerfile e resolvem TLS sozinhos. Duas notas antes de tentar:

- São **dois serviços**, um por Dockerfile, mais um Postgres gerenciado. O
  `docker-compose.prod.yml` não é aproveitado — e com ele vão embora as guardas `${VAR:?}`. Nesse
  caminho, o bloqueador 1.2 (`JWT_SECRET` com default) deixa de ser teórico: a plataforma injeta as
  variáveis direto no container, sem passar pela interpolação do Compose.
- `NEXT_PUBLIC_API_BASE_URL` precisa ser configurada como **argumento de build**, não como variável
  de ambiente do serviço. Plataformas que só oferecem variáveis de runtime não conseguem construir
  o frontend corretamente. Vale confirmar isso no painel antes de escolher a plataforma.

Tier gratuito: cabe o cenário A (sem Ollama), tipicamente com hibernação após inatividade — o
primeiro acesso depois de dormir leva dezenas de segundos e a JVM demora ~8 s só para subir
(medido). O cenário B não cabe em tier gratuito nenhum.

## 6. Verificação depois de subir

Na ordem, porque cada passo depende do anterior:

1. **Containers de pé.**
   `docker compose -f docker-compose.prod.yml --env-file .env.producao ps` — `postgres` e `backend`
   devem aparecer como `healthy`.
2. **Migrations.** `... logs backend | grep -i flyway` deve mostrar
   `Successfully applied 7 migrations` (ou `Schema is up to date` numa segunda subida).
3. **API viva.** `curl -i https://api.helpdesk.seu-dominio/api/v1/choices` → 200 com o JSON de
   enums. Endpoint público, é o mesmo do healthcheck.
4. **Login.**
   `curl -X POST https://api.../api/v1/auth/login -H 'Content-Type: application/json' -d '{"email":"admin@fadex.org.br","password":"admin123"}'`
   → 200 com `accessToken`. Se der 401, o seed não rodou (`APP_SEED_ENABLED`).
5. **JWT não é o default.** Confira no container:
   `docker compose ... exec backend printenv JWT_SECRET`. Se aparecer
   `trocar-por-valor-local...`, **pare o deploy**.
6. **Fuso.** `docker compose ... exec backend date` deve mostrar o horário de Fortaleza, não UTC.
   Com o host em UTC e sem `TZ`, os carimbos aparecem três horas adiantados na tela — as entidades
   usam `LocalDateTime`, que não carrega fuso.
7. **O frontend fala com a API certa.** Abra o site, F12, aba Rede, faça login e confirme que a
   requisição vai para o domínio da API. **Se aparecer `localhost:8080`, o bloqueador 1.1 não foi
   corrigido** — e nada mais vai funcionar.
8. **CORS.** Um erro de CORS no console do navegador com a chamada saindo para o domínio certo
   significa `CORS_ALLOWED_ORIGINS` errada: confira esquema (`https`), porta e ausência de barra
   final.
9. **Classificação.** Crie um chamado e espere até ~10 s (`AI_WORKER_INTERVAL_MILLIS`). Categoria e
   prioridade devem deixar de ser `PENDENTE`. Em `GET /api/v1/ai/jobs` (ADMIN), com a IA desligada,
   o esperado é `CLASSIFICATION` em `DONE` e `EMBEDDING` em `FAILED` — conforme o achado 1.3.
10. **SSE.** Duas abas com usuários diferentes; altere um chamado numa e veja a outra reagir. É o
    recurso mais sensível a proxy reverso.
11. **E-mail.** Sem `SMTP_HOST` real, o envio falha. A falha fica no log e não derruba o fluxo do
    chamado (timeouts limitados a 5 s), mas nenhuma notificação por e-mail chega.

### Rollback

`docker compose -f docker-compose.prod.yml --env-file .env.producao down` derruba tudo **sem**
apagar o volume. Com `-v`, apaga o banco: o volume `postgres-data` é o único estado que importa.
Não existe migration de rollback — Flyway aqui só avança.

## 7. O que não foi validado

Deploy sem plataforma não se prova. Foi verificado localmente, com Docker:

- `docker compose -f docker-compose.prod.yml config` falha sem as cinco variáveis obrigatórias, e
  passa com o `.env` preenchido, nos dois modos (com e sem `--profile ia`).
- O build do frontend **não** carrega `NEXT_PUBLIC_API_BASE_URL` para o bundle; o ajuste sugerido
  em 1.1 faz carregar.
- A stack sobe contra `postgres:17-alpine` sem pgvector, com os placeholders sobrescritos: sete
  migrations, login 200, criação de chamado 201, indicadores 200, classificação por heurística
  concluída.
- `SPRING_DATASOURCE_*` funciona com `SPRING_PROFILES_ACTIVE=prod`; `DB_*` não.
- `SPRING_APPLICATION_JSON` vazio não atrapalha o boot.
- O comando do healthcheck do backend, executado dentro do container: sai com código 0, e
  `/api/v1/choices` responde 200 sem autenticação.
- Consumo de memória e disco, e a latência de inferência, nos números da seção 2.1.

**Não foi verificado, e não pode ser sem uma conta:**

- Nada em plataforma alguma. Sem conta, sem domínio, sem IP público.
- TLS, certificado, proxy reverso e o comportamento do SSE atrás de proxy.
- Conexão com Postgres gerenciado, `sslmode=require`, e se o usuário da aplicação tem permissão de
  `CREATE EXTENSION` em algum provedor específico.
- Envio real de e-mail por SMTP externo.
- O cenário B ponta a ponta em máquina remota: o Ollama foi medido nesta máquina, com 12 vCPU, e um
  VPS de 2 vCPU vai se comportar pior do que os números da seção 2.1.
- Custo. Os valores de VPS citados são ordem de grandeza, não cotação.
